# План: полноценное меню Wi-Fi в текущем UI

## Цель

Добавить полноценное пользовательское меню Wi-Fi в текущую прошивку на базе `TFT_COLOR_UI`, не переключая проект на `TFT_LVGL_UI` и не включая `mks_ui` целиком.

Итоговый результат:

- пользователь видит состояние Wi-Fi прямо в интерфейсе принтера;
- пользователь может запустить поиск сетей;
- пользователь может выбрать сеть;
- пользователь может ввести пароль;
- принтер может отправить параметры в Wi-Fi модуль и попытаться подключиться;
- в интерфейсе отображаются текущая сеть, режим и IP;
- текущий UI прошивки `v1.3` сохраняется.

## Почему выбран этот путь

В проекте уже есть готовая реализация Wi-Fi меню в `mks_ui`, но она относится к `TFT_LVGL_UI` и в текущей сборке исключена из компиляции через `platformio.ini`.

Текущая рабочая сборка использует:

- `TFT_COLOR_UI`
- стандартное меню Marlin
- собственный транспорт Wi-Fi из `Marlin/src/module/mks_wifi`

Поэтому безопаснее и дешевле по рискам перенести нужную функциональность в текущий UI, чем переключать всю прошивку на другой интерфейс.

## Архитектурное решение

### Что не делаем

- не включаем `mks_ui` в сборку;
- не включаем `TFT_LVGL_UI`;
- не меняем базовый интерфейс `v1.3`;
- не переносим весь LVGL-код как есть.

### Что делаем

Добавляем поверх текущего UI:

- новое меню Wi-Fi в дереве меню Marlin;
- несколько экранов/состояний для работы с Wi-Fi;
- слой команд в `mks_wifi.cpp`, который сможет:
  - запросить статус,
  - запросить сканирование сетей,
  - хранить список найденных сетей,
  - принять новый SSID/пароль,
  - отправить параметры в модуль,
  - инициировать переподключение.

## Предлагаемая структура реализации

### Этап 1. Подготовить Wi-Fi backend для меню

Цель: привести `mks_wifi` к состоянию, когда им можно управлять из обычного UI.

Изменения:

- расширить `mks_wifi.h` структурами состояния:
  - текущий статус соединения;
  - текущая сеть;
  - режим;
  - IP;
  - буфер SSID;
  - буфер пароля;
  - список найденных сетей;
  - флаги "идет сканирование", "нужен connect", "есть обновление списка".
- выделить публичные функции:
  - `wifi_request_scan()`
  - `wifi_has_scan_results()`
  - `wifi_get_scan_count()`
  - `wifi_get_scan_ssid(index)`
  - `wifi_set_credentials(ssid, password)`
  - `wifi_connect()`
  - `wifi_reconnect()`
  - `wifi_is_connected()`
  - `wifi_get_ip()`
  - `wifi_get_mode()`
  - `wifi_get_current_ssid()`
- перенести или адаптировать протокольные куски из `mks_ui/wifi_module.cpp` только в необходимом объеме.

Результат этапа:

- backend можно вызывать без LVGL;
- логика Wi-Fi не зависит от `mks_ui`;
- меню сможет работать через простой API.

### Этап 2. Добавить базовый экран Wi-Fi в обычное меню

Цель: пользователь должен видеть, что Wi-Fi жив и что с ним происходит.

Изменения:

- добавить пункт `Wi-Fi` в меню настроек или информации;
- создать отдельный экран/подменю с пунктами:
  - `Status`
  - `Current Network`
  - `IP Address`
  - `Scan Networks`
  - `Reconnect`
  - `Saved SSID`
  - `Enter Password`
  - `Connect`

Рекомендуемое место интеграции:

- начать с `menu_info.cpp` как с уже существующего места Wi-Fi;
- после этого перенести пункт в более удобное пользовательское меню через `menu_configuration.cpp`.

Результат этапа:

- в прошивке появляется видимое полноценное меню Wi-Fi;
- без ввода пароля уже можно смотреть статус и работать с переподключением.

### Этап 3. Реализовать сканирование сетей

Цель: получить список сетей из Wi-Fi модуля и отобразить его в текущем UI.

Изменения:

- добавить в backend команду запроса списка сетей;
- добавить парсинг пакетов со списком сетей;
- хранить список в компактном статическом буфере;
- сделать отдельный экран выбора сети.

UI-поведение:

- пользователь нажимает `Scan Networks`;
- прошивка показывает `Scanning...`;
- после завершения открывается список SSID;
- при выборе SSID оно копируется в текущий буфер настроек.

Результат этапа:

- выбор сети идет из списка, а не ручным вводом SSID.

### Этап 4. Реализовать ввод пароля

Цель: пользователь может ввести пароль без перехода на LVGL UI.

Варианты:

1. Переиспользовать существующий touch-friendly экран ввода из текущего `TFT_COLOR_UI`, если это возможно малыми изменениями.
2. Сделать отдельный упрощенный экран экранной клавиатуры специально для Wi-Fi.

Рекомендуемый вариант:

- сделать минимальный локальный экран ввода пароля под текущий UI, без попытки тащить весь `draw_keyboard.cpp`.

Требования:

- ввод латиницы, цифр и основных символов пароля;
- очистка строки;
- подтверждение;
- отмена.

Результат этапа:

- пользователь может выбрать SSID и ввести пароль прямо на принтере.

### Этап 5. Подключение и переподключение

Цель: после выбора сети и ввода пароля принтер реально отправляет настройки в модуль.

Изменения:

- реализовать отправку параметров по протоколу, аналогично `package_to_wifi(WIFI_PARA_SET, ...)`;
- адаптировать только необходимый кусок формата пакета;
- после отправки инициировать команду подключения;
- обновить отображение статуса в UI.

UI-поведение:

- после `Connect` показать `Connecting...`;
- при успехе показать сеть и IP;
- при ошибке показать `Failed` и оставить пользователя в Wi-Fi меню.

Результат этапа:

- функциональность становится законченной с точки зрения пользователя.

### Этап 6. Сохранение и повторное использование настроек

Цель: не заставлять пользователя вводить пароль каждый раз.

Варианты хранения:

1. Хранить только в самом Wi-Fi модуле.
2. Хранить в EEPROM принтера.
3. Хранить в `printer_settings.ini`.

Рекомендуемый первый шаг:

- сначала опираться на сохранение в Wi-Fi модуле;
- на стороне прошивки хранить только текущие рабочие буферы;
- затем отдельным шагом добавить сохранение SSID и режима в EEPROM/ini.

Причина:

- это уменьшает первый объем изменений;
- сначала надо добиться стабильного подключения;
- потом уже решать постоянное хранение.

## Предлагаемый порядок реализации

### Фаза A. Минимально рабочая версия

- подготовить backend в `mks_wifi`;
- добавить экран Wi-Fi статуса;
- добавить `Reconnect`;
- добавить `Set SSID` и `Set Password` через временный ручной ввод;
- добавить `Connect`.

Результат:

- уже можно реально подключаться без стока.

### Фаза B. Удобная версия

- добавить `Scan Networks`;
- добавить экран выбора сети;
- улучшить сообщения об ошибках;
- почистить интерфейс.

Результат:

- Wi-Fi меню становится полноценным и удобным.

### Фаза C. Доработка хранения

- сохранить режим/SSID в EEPROM или `printer_settings.ini`;
- восстановление после перезагрузки;
- синхронизация с уже существующим механизмом `M5000/M5001`.

## Риски

### Высокие

- протокол обмена с Wi-Fi модулем частично живет в двух разных реализациях (`mks_wifi` и `mks_ui/wifi_module`);
- список сетей и команды подключения могут иметь нюансы, которые не покрываются текущим `mks_wifi.cpp`;
- touch UI для ввода текста в `TFT_COLOR_UI` может потребовать отдельной локальной реализации.

### Средние

- нехватка RAM под список сетей и строки;
- конфликт логики с существующим обработчиком serial-пакетов Wi-Fi;
- различия поведения модулей на разных ревизиях плат.

### Низкие

- добавление пункта меню статуса Wi-Fi;
- показ IP, режима и текущей сети;
- переподключение через существующий backend.

## Что нужно проверить до начала кодинга

1. Какие типы пакетов реально приходят от Wi-Fi модуля в текущей связке.
2. Может ли текущий `mks_wifi.cpp` уже принимать список сетей, или нужен новый разбор `ESP_TYPE_WIFI_LIST`.
3. Есть ли в `TFT_COLOR_UI` удобная заготовка для текстового ввода, пригодная для повторного использования.
4. Где лучше разместить новое меню: в `Information` или в `Configuration`.

## Рекомендуемое следующее действие

Начать с Фазы A и первым делом сделать backend-слой в `Marlin/src/module/mks_wifi/`, чтобы не смешивать UI и протокол в одном изменении.

Если двигаться дальше по этому плану, следующим рабочим шагом должен быть:

- анализ и перенос только нужных протокольных команд из `Marlin/src/lcd/extui/mks_ui/wifi_module.cpp`
- в `Marlin/src/module/mks_wifi/mks_wifi.cpp`

## Отдельно про безопасность изменений

Перед любыми тестами прошивки:

- сохранить текущие настройки принтера через `M5000`;
- отдельно записать текущий `M851`;
- не использовать `M502` до завершения работ;
- после тестовой прошивки проверять Z-offset и BLTouch отдельно.
